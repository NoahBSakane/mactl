# 委譲プロトコル

## 指示フォーマット(委譲を実行する際)

```text
【指示先】Codex CLI / agy / Muse / Grok Build / サブエージェント
【優先度】High / Medium / Low
【タスク内容】(スコープを一文で)
【成功基準】(完了判定できる具体的な条件)
【報告形式】変更点 / 残課題 / 影響範囲
```

## 報告受領フォーマット(委譲先からの報告で必ず確認する)

- 変更点: 何をどう変えたか
- 残課題: 未対応・保留にした事項
- 影響範囲: 副作用が及びうる箇所

「完了しました」だけで上記が欠けている報告は受理しない。追撃質問するか、自分で確認して埋める。

## コンテキスト共有

- 渡す: タスクスコープ・関連ファイルパス・成功基準・関係する指示ファイル(AGENTS.md等)の制約
- 渡さない: 無関係な会話履歴・機密情報・固まっていない検討中の代替案

## エスカレーション条件(司令塔が直接介入する)

- 報告フォーマットが欠落している、または成功基準を満たしていない
- 破壊的操作・外部公開を伴う新たな判断が発生した
- 実行中にスコープが二転三転した
- adversarialレビューで、生成物・報告内容に矛盾や漏れが見つかった

## 品質ゲート

- 外部エージェントの生成物(コードもレビュー結果も調査結果も)は、採用前に必ず司令塔がレビューする。完了報告を鵜呑みにしない。調査・解析結果は出典と再現性を確認する。
- レビューを外部に任せるときの委譲範囲は、指摘の列挙(観点出し・抜け漏れ探し)まで。どの指摘を採用するかは司令塔が決める。
- 同じエージェントが書いたコードを、そのエージェント自身にレビューさせない(自己レビューは歯止めにならない)。別のエージェントか司令塔が見る。
- 上の受領フォーマットを満たしてから完了とする。

## トークン・利用枠の節約

- 数行〜数箇所の機械的修正は委譲のオーバーヘッドの方が大きい。自分で直接やる。
- 「既存の挙動を1バイトも変えない」ことが成功条件の修正は、新規生成寄りのエージェントへ出さない。
- effortは案件の重さに合わせて下げる。利用枠が小さい環境では、失敗時にリトライで粘らず、別のエージェントに切り替えるか自分で処理する。
- 外部CLIへの委譲は、司令塔自身の使用枠とは別枠の消費になる。実装量が大きいほど外へ逃がす価値がある。

## Codexへ委譲するときの落とし穴(2026-10-08)

- 環境変数 `AGENT_DELEGATED_BY` だけでは足りない。プロンプトの先頭に「あなたは委譲先で、構成の提示・承認・質問は不要。依頼されたタスクだけを実行する」と明記する。明記しないと、Codex側のフックが実装前の構成承認を促して質問UIの回答待ちに入り、何も編集せずに終了することがある(gpt-6.1-sol で再現。軽量モデルでは再現しない)。
- 長い委譲の指示・出力・レビュー結果は、一晩で消える一時領域(`/private/tmp` など)だけに置かない。リポジトリ内(`.agent-handoff/` など、`.git/info/exclude` に追加)か永続の場所にも残す。出力はファイルへ直接リダイレクトし、完了マーカー(`exit=`)と停滞を Monitor で見張る。プロセスの生存だけでなく、作業ツリーに変更が出ているかも確認する。
- `npm test` などの検証は、委譲先の報告を信じず自分で再実行する(サンドボックスで失敗した、過大な報告があった)。
