# propose-rule

配備された指示ファイルは、`install.sh` が管理しており、エージェントが直接編集することはできない(編集しようとすると、hookが拒否する)。ルールを足したい・変えたいときは、**提案として出す**。提案は、あとで `triage-rules` skill により、全体に行き渡らせるか、特定のエージェントやプロジェクトだけのルールにするか、却下するかを検討される。

## 提案してよいもの

- ユーザーの訂正や指示から学んだ、**今後も繰り返し守るべき**ふるまい(「〇〇のときは△△する」)。
- 自分のメモリ(自動メモリなど)に溜まった、ふるまいに関わる好み。
- 指示ファイルの記述が、実態と食い違っている・古い、という気づき(修正案を提案文にする)。

一度きりの事情、プロジェクトの事実(それはプロジェクトの `AGENTS.md` や `~/.knowledge/` の知識)、秘密や個人情報は、提案にしない。

## 手順

1. **重複を確認する。** `~/AGENTS.md`(共通ルール)と、自分に固有の指示ファイルを読み、すでに同じ内容が無いか確かめる。ある場合は、提案せず、そのルールに従うだけでよい。
2. **追記する。** `~/.knowledge/rule-proposals.md` の**末尾に追記**する(既存のエントリを書き換えない)。書式は、そのファイルの冒頭に書いてある。

   ```bash
   cat >> ~/.knowledge/rule-proposals.md <<'ENTRY'

   ## 2026-10-07 <自分のエージェント名> — 提案: <一行の要約>

   - 提案文: <命令形で1〜3行>
   - 動機: <何が起きたか>
   - 想定範囲: <全体 / 固有:エージェント名 / プロジェクト:パス / 知識:領域> — <理由>
   - 状態: 未検討
   ENTRY
   ```

   提案文は、他のエージェントでも通じる言い方(ツール固有の語を避ける)で書く。範囲の見立てに迷ったら「全体」と書かず、理由を添えて迷っていると書く。
3. **ユーザーに一言伝える。** 「ルール提案を `rule-proposals.md` に追記しました(要約)」と報告する。採用はユーザーの承認後なので、今回の作業では、そのルールを前提にしない。

## ユーザーが「〇〇に追記して」と明示したとき

指示ファイルを直接編集せず、同じく提案として追記する(動機に「ユーザーの明示的な指示」と書く)。ユーザーが即時の反映を望むなら、`triage-rules` skill の手順(リポジトリの `src/` を直して `install.sh` で配備)を、その場で進める。
